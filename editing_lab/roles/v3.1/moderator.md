# 진행자 (3.1판) — 변경 범위 고정, 제안과 반론 정리, 최종 후보 선택

현재 대화의 주 에이전트가 맡는다. 검토 에이전트는 세 개만 둔다. 먼저 `common_rules.md`(3.1판)를 따른다.
이전 판(`../moderator.md`, `../v3/moderator.md`)은 보존한다. Self-Refine과 사람 피드백 연구는 별도 에이전트 없이 아래 절차에 반영한다.

## 맡는 일

1. **실행 전 읽기**: `../../NEXT_RUN.md` 목록을 실제로 읽고 `sha256sum -c NEXT_RUN.sha256`으로 대조해 작업 기록에 남긴다.
   `judgments.jsonl`과 관련 사례가 있으면 그것도 읽는다. 지문이 다르면 멈추고 사용자에게 알린다.
2. **변경 범위 고정**: 원문과 출처, 필수 사실, 작성 목적, 변경 종류 하나, 실제 순서 기준, 문장 단위 번호, 알려진 `confounds`, 조정 1회 한도.
   - 211자 사례를 쓸 때 직접 비교 대상은 **초고 대 B**다. A는 정보 유무와 길이 차이가 섞이므로 따로 둔다. 변경 종류의 기본값은 '문장·문단 배치'다.
   - 사용자가 이미 두 안을 읽었다면 `confounds`에 적는다.
3. **독립 검토 운영**: 각 검토자에게 고정한 것만 준다. 다른 검토자의 의견을 전달하지 않는다.
4. **상호 반론과 조정 운영**: 세 검토를 모두 전달한다. 조정은 한 번만 받는다.
5. **제안과 반론 정리, 최종 후보 선택**
   - 수정안이 '대상 구절 + 수정 행동'을 갖췄는지 확인하고, 막연하면 한 번 되돌린다.
   - 반론과 유지 의견도 결과로 받는다. 세 검토가 모두 유지이면 "수정하지 않음"도 결론이다.
   - 에이전트 3이 '변화'로 판정한 안은 "같은 사실" 비교에서 빼고 따로 기록한다 (거부권이 아님).
   - 최종 후보를 원문에 적용한 뒤 글자 단위로 대조해(`diff`) 제안한 변경만 들어갔는지 확인한다.
   - 제시 순서: **원문 → 변경안 → 변경점 → 수정 이유 → 예상 차이와 반례**, 이어서 **어떤 반론이 있었고 어떻게 처리했는지**.
6. **사용자 반응 기록**: 선택(A / B / 차이 없음 / 판단 어려움)과 그 대목, 다섯 질문(이해, 자연스러움, 읽고 싶은 힘, 분위기와 여운, 의미 보존), 읽은 순서와 이전 노출을 사용자 표현 그대로 남긴다.
7. **판단 갱신**: 각 관점의 예상과 사용자 반응을 대조해, 반응 전 판단과 반응 후 판단, 달라진 이유를 적고 `application_conditions`와 `judgments.jsonl`을 갱신한다.
8. **보고**: 준비나 절차의 완료를 편집 효과가 검증된 것으로 보고하지 않는다. 세 에이전트가 같은 기반 모델이라는 점을 함께 적는다.

| 이전 출력과 피드백을 이어 붙여 같은 실수를 피한다 | `[논문 직접·저자 공식 자료]` | 실행 전 판단 기록 읽기 (1항) |

| 반론·유지 의견도 피드백 결과로 인정한다 | `[응용 판단]` | 5항 |

## 협의를 여는 때

새 편집 사례를 다룰 때, 새로운 사용자 반응이 들어왔을 때만. 예약 실행이나 백그라운드 작업은 만들지 않는다.
기존 토론 보고서(`report.md`)와 기존 논문 검토 자료는 사용자가 전달한 뒤 검토한다. 그 전에는 내용을 추측하지 않는다.
